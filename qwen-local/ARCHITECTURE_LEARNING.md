# 从单人本地聊天到多用户系统：更新与工作原理

后续新增的多人法庭功能见COURTS_UPDATE.md：保留个人聊天，加入10人房间、成员权限、两种阶段与SSE共享AI同步。下文主要解释此前的基础架构更新。

本文以当前项目代码为准，面向刚接触后端部署、数据库和大模型服务的读者。项目位置：E:\qwen-local\qwen-local。

## 1. 这次主要改了什么

原来的方案是：网页 → FastAPI → 同一程序加载模型 → SQLite保存聊天。模型生成有全局锁，生成请求主要串行执行。

当前方案把网页业务与GPU推理解耦，并补上账号、数据隔离、有限并发和公网入口配置。

| 部分 | 原来的方式 | 当前方式 | 为什么这样改 |
|---|---|---|---|
| 模型推理 | 后端直接使用Transformers加载模型 | 独立vLLM容器加载本地Qwen3-8B | 专门的推理服务调度多个请求，业务重启不必重新加载模型 |
| 模型精度 | 旧版包含INT8/NF4量化路径 | 当前FP16 | 当前实测配置的精度与显存占用发生变化，速度不能只归因于vLLM |
| 并发 | 全局生成锁，主要串行 | 最多5个生成请求＋5个等待位置 | 让多个账号同时获得输出，并限制超负荷请求 |
| 数据存储 | SQLite文件 | PostgreSQL服务 | 提供连接池、并发事务和明确的数据关系，便于后续扩展 |
| 用户体系 | 单人测试使用 | 注册、登录、退出、账号数据隔离 | 每个人只访问自己的会话 |
| 登录状态 | 没有当前多用户机制 | Redis保存登录会话和认证限流计数 | 支持凭证过期、退出撤销和频率限制 |
| 数据库结构更新 | 初始化时建表 | Alembic迁移 | 记录数据库结构版本，以后可有序升级 |
| 运行环境 | 主要依赖Windows Python环境 | Windows后端＋WSL2/Docker Linux服务 | 固定基础服务配置，减少手动安装差异 |
| 外网访问 | 仅127.0.0.1访问 | NATAPP HTTPS入口及公网后端配置 | 校园网中的电脑可通过主动连接中转向外提供网页 |
| 前端 | 聊天页面 | 新增登录注册、退出、排队显示，统一视觉风格 | 支持多用户操作与等待反馈 |

旧SQLite测试对话没有迁移，data/chat.db仍保留，但当前服务不读写它。旧model_service.py及旧启动脚本也保留，当前入口不调用它们。

## 2. 当前整体架构

```text
浏览器（登录和聊天）
   │ 公网HTTPS，或本机HTTP
   ▼
NATAPP入口与本机客户端（公网访问时经过）
   │ 转发到127.0.0.1:8000
   ▼
FastAPI业务后端（Windows Python，单worker）
   ├── PostgreSQL :5432 → 用户、会话、消息
   ├── Redis :6379      → 登录凭证、认证限流
   └── 进程内调度       → 5个生成名额、5个等待位置
           │ 本地HTTP：/v1/chat/completions
           ▼
      vLLM容器 :8001
           │ 本地模型权重、GPU执行
           ▼
      Qwen3-8B + RTX 4090
```

端口是服务的网络入口，8000和8001分别属于两个不同服务。浏览器访问8000，业务后端调用8001；5432和6379用于数据服务。当前这四个端口都只绑定127.0.0.1，公网只通过隧道转发网页入口。

## 3. WSL2、Ubuntu、Docker分别是什么

### Windows与WSL2

WSL2提供在Windows上运行Linux环境的能力。Ubuntu是安装在WSL2中的Linux发行版。它们没有把整个Windows项目强制迁移到Ubuntu。

当前FastAPI仍由Windows上的Anaconda Python运行。Docker Desktop使用WSL2后端承载Linux容器，容器里的PostgreSQL、Redis和vLLM运行Linux程序。Ubuntu的Docker集成让你也能从Ubuntu终端操作Docker；它不意味着每个容器都装在你的Ubuntu发行版里。

### Docker的四个概念

- **镜像**：预先准备好的程序与运行环境模板，例如postgres:17。
- **容器**：根据镜像启动的运行实例，可以启动、停止和重建。
- **数据卷**：独立保存持久数据，避免数据只存在于容器内部。
- **Compose**：用YAML文件描述服务、端口、挂载、环境变量和健康检查，再统一启动。

compose.yaml启动PostgreSQL和Redis；compose.inference.yaml启动vLLM。这两份配置属于两个Compose项目。

模型目录通过只读绑定挂载进入vLLM容器：Windows的models/Qwen3-8B映射为容器里的/models/Qwen3-8B。模型文件没有因此变成云端模型。

Docker不是另一块GPU，也不会凭空增加显存；gpus: all让容器访问现有4090。容器能运行nvidia-smi说明GPU访问链路打通，但仍需真正启动模型才能验证推理。

## 4. vLLM是什么，为什么可以同时回答

vLLM是大模型推理服务程序，不是模型本身。Qwen3-8B是模型权重；vLLM负责加载权重、处理请求、管理推理状态并使用GPU计算。

旧版的全局锁让一个生成任务完成后下一个才能进入。vLLM可以通过连续批处理，在GPU计算步骤中组织多个活动请求；新请求与完成的请求可随调度加入、退出。它还使用专门的KV缓存管理方案，保存生成时需要的注意力中间状态。

因此多个用户可以同时持续收到内容。它不是为每个用户加载一份8B模型，也不等于五块GPU完全独立计算；各请求共享模型权重、显存和计算资源。负载增加时单个请求的速度和首字延迟可能变化。

当前配置：

| 参数 | 当前值 | 含义 |
|---|---|---|
| 模型目录 | /models/Qwen3-8B | 读取本地权重 |
| served-model-name | qwen3-8b | API请求中使用的服务模型名 |
| dtype | half | FP16计算精度 |
| max-model-len | 4096 | 单请求总上下文上限，包括输入和输出 |
| max-num-seqs | 5 | 推理调度允许的最大活动序列数 |
| gpu-memory-utilization | 0.80 | vLLM显存预算参数，不是整张卡所有程序的占用上限 |
| enforce-eager | 开启 | 使用eager执行模式，当前没有使用CUDA Graph优化路径 |

业务代码输入预算3072 token、输出上限1024 token，并关闭Qwen思考模式。超过输入预算时优先去掉最旧历史轮次，保留系统提示和当前问题；当前问题本身仍过长时拒绝请求。数据库中的旧历史不因此删除。

token是模型处理文本的单位，不等于一个汉字，也不等于一个英文单词。回答可能因为达到输出上限而截断。

当前速度提升来自推理实现、调度、缓存以及精度等多方面变化，不能仅凭体感把全部提升归于某一项。

## 5. 本地API是否意味着使用云端模型

不意味着。API只是程序间的调用约定。

后端调用http://127.0.0.1:8001/v1/chat/completions，地址指向这台电脑上的vLLM。接口格式与OpenAI兼容，方便使用通用HTTP客户端，但模型计算仍发生在本机。

已下载模型和依赖后，本机聊天不依赖公网模型接口。公网访问需要NATAPP和网络，聊天内容会经过中转服务，因此“本机推理”不等于“公网聊天数据完全不离开电脑”。

模型自称某个在线产品，也不是联网调用的证据。回答身份受训练数据和提示影响，可能说错；部署事实应以代码、网络地址和运行日志为准。

## 6. PostgreSQL、SQLAlchemy、Alembic分别负责什么

PostgreSQL是数据库服务；SQLAlchemy是Python与数据库交互的工具，管理连接、表映射和事务；psycopg是连接PostgreSQL的驱动；Alembic管理数据库结构升级。

当前表关系：

```text
users 用户
  └── conversations 会话（user_id指向用户）
        └── messages 消息（conversation_id指向会话）

alembic_version 保存数据库结构迁移版本
```

每次查询会话时，后端同时验证账号归属。即使用户猜到别人的会话ID，也不能因此读取或删除其记录。

当前连接池pool_size=5、max_overflow=5，表示数据库连接的池配置，不表示最多只能注册10个用户。连接是短事务期间借用的资源，执行完会归还，不会在整段模型生成期间一直占住数据库连接。

Alembic命令：

```powershell
& 'D:\Anaconda\envs\qwen-local-new\python.exe' -m alembic upgrade head
```

它将数据库结构升级到已有迁移的最新版本，并不会自动替你迁移旧SQLite的数据。以后修改表字段，需要编写和检查新的迁移，再执行升级。

DBeaver是数据库图形化客户端，便于查看表和数据；关闭DBeaver不会停止PostgreSQL。

## 7. Redis现在用于什么

当前Redis有两项主要用途：

1. 保存随机登录凭证的SHA256索引与用户ID，设置24小时过期时间。
2. 保存登录/注册频率计数，用原子操作避免并发计数出错。

用户密码不是保存在Redis中的明文：PostgreSQL保存Argon2哈希。浏览器保存HttpOnly登录Cookie，后端用它查询Redis并验证用户是否有效。退出会撤销对应凭证。

**当前Redis不是消息队列，也没有用来缓存所有模型回答。** Redis能够做很多事，但安装它不代表这些功能已经实现。

公网入口会让多个成员的连接在后端体现为相同入口来源。当前不信任传入的转发IP，认证限流可能由成员共享：每五分钟30次登录/注册操作。

## 8. 一次聊天请求如何完成

1. 浏览器发送问题及会话ID，并携带登录Cookie。
2. 后端验证网页来源、登录凭证和会话所属用户。
3. 查询历史记录，尝试预留生成名额；每账号只允许一个活动或排队请求。
4. 调用vLLM的/tokenize检查输入长度，必要时裁剪发送给模型的历史；保存当前用户消息。
5. 有名额就开始生成，没有名额就等待FIFO队列，并向网页发送排队位置。
6. inference_client.py通过异步HTTP调用vLLM，接收增量文本。
7. FastAPI以SSE事件把文本继续转发给网页，网页不断追加显示。
8. 正常生成完成后，保存完整助手回答，返回统计并释放名额，让下一个等待请求进入。

SSE是服务器通过一个持续HTTP响应向浏览器发送事件的方式。它适合单向逐步输出，不是WebSocket，也不是每个字都发起一次独立请求。上游vLLM与下游网页是两段不同的流。

失败、排队超时或断线时会释放占用；已保存的用户问题保留，不完整助手回答不按成功回答保存。模型上游连接会关闭，实际资源回收仍由推理服务处理。

## 9. 并发、异步、多线程和消息队列的区别

- **并发**：多个任务在同一时间段内推进，例如五个人都看到回答增长。
- **异步I/O**：等待网络响应时让事件循环处理其他请求，适合流式HTTP；不是让CPU计算自动加速。
- **线程**：可执行阻塞任务，当前部分短数据库操作通过asyncio.to_thread运行，避免阻塞异步事件循环。
- **进程/worker**：独立业务进程，增加后内存中的队列不会自动共享。
- **消息队列**：在生产者和消费者之间组织任务，可实现持久任务、重试、跨进程协调等，但需要另行设计。

当前FastAPI只有一个worker，generation_queue.py使用asyncio.Event和内存FIFO队列：5个生成名额、5个等待位置、等待最多120秒。第11个同时占用的请求返回429；同账号重复占用也拒绝。

不要直接把workers改成4：这会产生4套独立名额状态，破坏当前统一限制。也不要认为增加Python线程数可以让4090无限并发。扩展到多实例时，需要共享调度、请求状态和取消机制。

## 10. 实际测试说明了什么

| 并发 | 每路输入 | 每路输出 | 每路耗时约 |
|---|---:|---:|---:|
| 4 | 1637 token | 512 token | 12.3秒 |
| 5 | 1637 token | 512 token | 11.7秒 |
| 5 | 2917 token | 1024 token | 25秒 |

各组输出流存在共同重叠区间；11账号测试验证了5生成、5排队、1拒绝，以及接受请求分别入库。

这些是有限轮次、合成提示测试，部分受前缀缓存影响。不能据此保证所有真实问题同样快，也不是长期运行稳定性认证。五六人实验组可先试运行，根据真实等待时间、显存与报错调整。

## 11. 公网入口如何工作，哪些还没完成

NATAPP客户端主动连接中转服务器，不要求学校路由器开放入站端口。同学访问HTTPS域名，中转通过已建立的隧道把请求交给本机8000。

域名HTTPS在公网入口处理；本机后端仍是HTTP，所以控制台应勾选域名HTTPS，不勾选本地HTTPS。serve_public.py只允许https://zss.nat200.top的网页来源，并开启Secure Cookie。浏览器应使用HTTPS链接登录。

旧节点120.26.87.232:4443直连超时；新节点47.97.153.27:4443已由你验证可连接。但这只证明新节点TCP可达，不代表VIP隧道已切换或HTTPS聊天验收完成。需要平台完成节点绑定，客户端Online，再测试公网登录、逐字输出和多账号并发。

当前尚未完成完整的企业级运维体系：自动备份与恢复演练、后台账号管理、注册邀请、监控告警、服务自动启动、多实例部署等不能视为已经具备。当前是用于学习和实验组试用的多用户基础版本。

## 12. 建议的学习顺序

1. 先读PROJECT_STRUCTURE.md和START_STOP.md，认识程序入口、端口和服务进程。
2. 阅读两份Compose配置，理解镜像、容器、挂载、数据卷和健康检查。
3. 用DBeaver观察用户、会话和消息的关联，再读database.py和迁移文件。
4. 阅读auth.py，理解密码哈希、Cookie、Redis会话与用户隔离。
5. 阅读inference_client.py，理解本地HTTP API、token预算和SSE流。
6. 阅读generation_queue.py与main.py，理解名额、排队、取消和资源释放。
7. 最后学习公网隧道、HTTPS、备份、监控与多实例调度。

可以做几个小实验：只重启网页后端，观察模型无须重载；关闭DBeaver，确认聊天仍正常；用两个浏览器账号同时发送问题；查看Redis登录会话TTL；观察一条新聊天如何在PostgreSQL中产生消息记录。不要用删除数据卷来测试持久化。

日常使用文档：START_STOP.md（本机启动关闭）、PUBLIC_ACCESS.md（公网配置）、ACCOUNTS.md（账号机制）、deploy/local/CAPACITY.md（并发测试）。
